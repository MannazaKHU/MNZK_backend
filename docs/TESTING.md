# 프론트 없이 모임 API 테스트

DB를 직접 수정할 필요가 없습니다. 프론트가 호출할 모임 생성·참여·응답 제출·조회 API를
테스트 스크립트나 Postman에서 호출하면 서버가 DB 저장과 추천을 처리합니다.

## 1. 임시 DB로 흐름만 확인

프로젝트 루트에서 실행합니다. API 서버·Docker를 따로 실행하지 않아도 됩니다.

```sh
.venv/bin/python -m scripts.check_meeting_flow
```

임시 SQLite와 AI/지도 mock을 사용합니다. 실제 Supabase DB를 수정하지 않고 외부 API를 호출하지 않습니다.
기본 2명이지만 `--members 4`처럼 인원을 바꿀 수 있습니다. 종료 시 임시 DB를 정리합니다.

검증 순서:

1. 서버·DB 준비 상태 확인
2. 모임 생성과 참여자 가입
3. N-1명까지 `waiting`인지 확인
4. 마지막 참여자 제출 후 `recommended`와 공통 시간 확인
5. GET으로 같은 추천이 저장·복원되는지 확인

임시 모임의 날짜는 한국 시간 기준 내일이고, 공통 시간은 18:00~20:00입니다.
공개된 역 좌표와 “조용한 카페”라는 일반 선호를 사용합니다. 자연어 조건 해석도 제출 흐름에 포함됩니다.

## 2. Railway 실제 연동 확인

아래 명령은 **배포 서버에 테스트 모임 1개와 참여자 데이터를 생성해 연결된 DB에 저장**합니다.
실제 AI·지역 검색·길찾기·활성화된 블로그 검색/추출의 이용량·크레딧이 발생할 수 있습니다.
DB에 직접 SQL을 실행하지 않으며, 테스트 모임은 실행 후 DB에 남습니다.

```sh
.venv/bin/python -m scripts.check_meeting_flow --base-url https://mnzkbackend-production.up.railway.app
```

마지막 제출은 추천 계산이 끝날 때까지 기다립니다. 요청 제한 시간 기본값은 180초이며
필요하면 `--timeout 240`으로 지정합니다. 시간 초과 시 중복 AI 호출을 막기 위해 자동 재전송하지 않습니다.
참여자 토큰과 초대 코드는 출력하거나 파일로 저장하지 않습니다.

출력의 `블로그 연결: live`, 검색·추출 횟수로 실제 보완 경로가 실행됐는지 확인합니다.
검색 성공이어도 유효한 인용이 부족하면 조건은 계속 미확인일 수 있습니다.

종료 코드:

- `0`: 모임 흐름·저장·재조회 성공, 추천 장소 있음
- `1`: HTTP/연결 오류 또는 기대한 흐름과 다름
- `2`: 처리는 완료됐으나 검증된 추천 0개. 확인 필요·이동정보 누락 후보 수를 함께 출력

처리가 완료됐지만 추천이 없다는 결과는 서비스 정책상 가능하며, 응답의 후보 평가를 확인해야 합니다.

## Postman으로 직접 확인하는 경우

API 계약은 [API.md](API.md)에 있습니다. 다음 순서로 호출하고 응답에서 받은 값을 다음 요청에 넣습니다.

1. `POST /api/meetings` → 모임 ID, 초대 코드, 방장 토큰
2. `POST /api/meetings/{id}/members` → 참여자 토큰
3. 각자의 Bearer 토큰으로 `PUT /api/meetings/{id}/members/me/submission`
4. `GET /api/meetings/{id}` → 대기·추천·처리 오류 확인

프론트 구현이 없어도 이 API들은 사용할 수 있습니다.
